## 3. Architecture

Modular monolith:

```
app/
  Domain/
    Shared/        Money, Quantity, NumberSequenceService, AuditLogger
    Locations/     LocationService (create/schedule/activate/deactivate, one-permanent rule), LocationContext, OperatingPeriodGuard, TerminalService
    Access/        user/role services, login event recorder
    Catalog/       PriceResolver, ProductService
    Pos/           CartPricer, CheckoutService (+ DTOs), IdempotencyGuard
    Orders/        OrderStatusMachine
    Payments/      CashTender, GcashTender
    Inventory/     InventoryLedger, StockReceiver, StockAdjuster
    Production/    RecipeResolver, ProductionPoster
    Cash/          ShiftService, ExpectedCashCalculator
    Refunds/       RefundService
    Reports/       report query objects
  Enums/           OrderStatus, PaymentStatus, OrderType, MovementType, ...
  Http/Controllers/{Admin,Pos,Staff}/   thin controllers
  Http/Requests/   Form Requests
  Policies/        per model; Gate::before only for nothing (no super-admin bypass except Owner role via permissions)
resources/js/
  layouts/  AdminLayout, PosLayout, StaffLayout
  pages/    admin/*, pos/*, staff/*
  components/ brand + shared UI
```

Principles: controllers validate (Form Request) → authorize (Policy/permission middleware) → call a Domain service → return Inertia response. Critical operations run in `DB::transaction` with explicit row locks. Vue holds only UI/cart-editing state; the server reprices everything.

### Phase 11 planned task: remove the tax feature (D-165)

The client is a non-VAT small business and wants tax removed, not just hidden (D-164 hid it in Phase 10b). Planned as one clean-up step in Phase 11, after the regression baseline is green, so checkout and refunds can be re-tested in full:

1. **Code:** delete `app/Domain/Tax` (`TaxCalculator`, `AppliedTax`, `TaxRules`), `TaxRule` and `OrderTaxLine` models, `TaxRuleController`, the `tax-rules` routes, `pages/admin/tax-rules`, the `tax_rule` morph-map entry, the `features.tax_rules` flag (config, `.env.example`, shared prop, sidebar `feature` field) and the `EnsureFeatureEnabled` middleware if nothing else uses it.
2. **Checkout and refunds:** take the tax step out of `CartPricer` / `PricedCart` and `CheckoutService` (grand total = subtotal − discount); simplify `Refundables` / `RefundableLine` (share = line total after discount).
3. **Receipts, POS and reports:** drop the tax lines from `OrderReceipt`, `ReceiptView.vue` and the POS quote; drop `tax` from `SalesFigures`, `SalesReport` and `types/reports.ts`. Keep the "not an official receipt/invoice" title (FR-087).
4. **Database:** a new forward migration drops `order_tax_lines` and `tax_rules`, then `orders.tax_total` and `order_items.tax_amount` (always 0.00, since tax was never on). Check first that every row is 0.00 on the user's `brevon_pos`; earlier migrations stay as they are. ERD updated.
5. **Tests and docs:** remove the T-TAX-1 tests and the D-164 flag test; add a test that checkout totals and refunds are unchanged; full `composer check`; mark FR-086 as out of scope (client decision) in DECISIONS, TEST_PLAN and README.

### Phase 11 planned task: remove the GCash check (D-168)

The client does not need a separate check of GCash payments. **GCash stays as a payment method.** The cashier confirms the transfer arrived before finishing the sale, and the reference number stays required and unique (D-039, D-109).

1. **Checkout:** a GCash payment is saved as **verified** at checkout (verified by the cashier, at the sale time), like cash; the order is `paid` at once. Remove the cashier "mark as received" shortcut and the `pending_verification` path from `CheckoutService` and the POS.
2. **Code:** delete `PaymentCheckController`, the `staff/payments` and `payments/{payment}/verify|reject` routes, the "GCash to check" page and sidebar link, the order-page check buttons, and the `payments.verify-ewallet` permission (catalog, seeder and Roles screen). Remove the "not received" flow (payment `failed`, order `unpaid`).
3. **Elsewhere:** take the "waiting for check" rules out of `RefundService` (GCash can always be refunded), `OrderWorkflow`, `ShiftSummary`, `SalesReport` (the sales definition becomes "paid and not cancelled"; collections lose the "Waiting for check" column) and the dashboard and receipts.
4. **Database:** no table is dropped. The `pending` and `failed` payment statuses stay valid for history. **Before switching**, list any GCash payments still pending on the user's `brevon_pos` and have a manager check them on the old screen, so nothing is left waiting.
5. **Tests and docs:** remove the GCash check tests (Phase 5) and the "waiting" cases in checkout, refund and report tests; add a test that a GCash sale is paid and verified at checkout. Update D-039, D-108, D-109, D-124 (replaced), D-153, D-156, D-158 and README.

### Phase 11 planned task: remove preparation (D-169)

The client does not need a preparation screen: every sale is finished at the counter.

1. **Checkout:** every order is **Completed** at checkout (D-108 changes: no more New/Preparing/Ready). Recipe-at-sale drinks still take their ingredients at checkout. 4. **Preparation staff role:** kept for bakers. It still drafts production batches and views stock, and lands on the production screen instead of the preparation board.
5. **Database:** no table is dropped. The old statuses stay valid for history, and `pickup_at` is dropped only if no order uses it. **Before switching**, any orders still New, Preparing or Ready on the user's `brevon_pos` must be completed or cancelled on the old screens; list them first.
6. **Tests and docs:** remove the preparation-board and cancel tests (Phase 5, parts of 9b) and the "Pickup at" cases. Update `RouteAuthorizationTest` and the role landing test. Update D-044, D-045, D-108, D-123 and D-125 (replaced), D-150, D-154, the Preparation staff role description and README.
